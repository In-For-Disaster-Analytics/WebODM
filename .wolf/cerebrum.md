## Key Learnings

- **Project:** WebODM
- **Description:** User-friendly, extendable application and API for processing aerial imagery.
- **[2026-07-22]** Django settings-module gotcha (discovered building a companion Tapis-auth integration for Label Studio, applies to any Django app with a settings file that reads back from `django.conf.settings` mid-import): if the settings module itself calls something that accesses `django.conf.settings.SOME_VAR` during its own top-level execution (e.g. `sentry.init_sentry()` -> `settings.SENTRY_DSN`), you cannot safely wrap it via a new module doing `from real_settings import *` — Django's lazy-settings recursion tolerance only works when the *same* module is re-entered (it finds the attribute already defined earlier in that file's own partial execution), not when a different wrapper module is in between. Fix: append overrides directly onto the tail of the existing settings file (and urls.py similarly) rather than introducing a new `DJANGO_SETTINGS_MODULE`/`ROOT_URLCONF`.
- **[2026-07-31]** Label Studio's Personal Access Token (the one an admin generates in Account & Settings, used by `coreplugins/embeddings/label_studio_client.py`) is a JWT **refresh** token, not a usable Bearer token on its own — confirmed against https://labelstud.io/guide/access_tokens (not guessed). Sending it directly as `Authorization: Bearer <PAT>` gets a 401 "Authentication credentials were not provided." It must first be exchanged via `POST /api/token/refresh` (body `{"refresh": "<PAT>"}` → response `{"access": "<token>"}`, ~5 min TTL); *that* access token goes in the Bearer header for every other endpoint. See bug-004. This is a real, current Label Studio API behavior — check it again if a future Label Studio upgrade changes auth, but don't assume the raw PAT ever works directly.
- **[2026-08-07]** Label Studio's project `title` field has a hard 50-character validation limit (confirmed via a live 400 error, not docs) — a title built by concatenating a WebODM task name plus a timestamp suffix with no length cap will exceed it whenever the task name is realistic-length, and the resulting 400 gets surfaced to the browser as a confusing 502 (the app's error-mapping treats non-2xx Label Studio responses as upstream failures). See bug-005.
- **[2026-08-07]** `embeddings-tapis-actors` embed-generate jobs are idempotent by design: `get_or_create_visit()` reuses an existing `visits` row for a task, and the actor's own DB upsert on `(tile_observation_id, encoder_id)` (Decision 56) means re-submitting the same embed request never duplicates work, only fills in what's missing. This is what makes a "Continue" action safe to implement as a plain re-POST to the existing `/embed` endpoint — no new resume-specific backend logic was needed. The ls6 Tapis App's own `maxMinutes: 60` (`embeddings-tapis-actors/ls6/app.json`) is the reason a run can die silently without ever updating its `visits`/`embeddings` rows, which is the root cause behind bug-005's "stuck on running forever" symptom.
- **[2026-08-07]** Real Tapis Jobs API shape, confirmed against the actually-installed `tapipy` package (v25.4.0, `tapipy/resources/openapi_v3-jobs.yml`) rather than guessed: `t.jobs.getJobStatus(jobUuid=...)` (operationId `getJobStatus`) returns an object with `.status` from the enum `PENDING, PROCESSING_INPUTS, STAGING_INPUTS, STAGING_JOB, SUBMITTING_JOB, QUEUED, RUNNING, ARCHIVING, BLOCKED, PAUSED, FINISHED, CANCELLED, FAILED`. `t.jobs.submitJob(**job_spec)` returns a `Job` object with a `.uuid` field — `apply_embed_generate()` had been discarding this return value entirely, which is exactly why job-status polling wasn't possible until bug-005's follow-up fix captured and persisted it.

## Decision Log

- **[2026-07-22]** WebODM's `app/auth/tapis_oauth2.py` `TapisOAuth2Backend` does not verify JWT signatures (see bug-003) — flagged as a security gap, not fixed in this repo since it was found while building an equivalent backend elsewhere. Recommend backporting real RS256 verification (via the Tapis Tenants API public key) here too.
- **[2026-08-07]** For bug-005 ("embed-generate stuck showing 'running' forever, can't restart"), first shipped a time-based idle-activity timeout (`WO_EMBED_GENERATE_TIMEOUT_MINUTES`, default 75) over two alternatives: (a) probing the Postgres advisory lock the actor holds during a run (`embeddings-tapis-actors/embed_generate/db.py`'s `run_lock`) — rejected because probing needs the run's `encoder_id`, which the status endpoint doesn't currently have; (b) a schema change to persist real job/run state — rejected as unnecessary complexity when `visits.created_at`/`embeddings.created_at` (both already existing columns) give a good-enough real signal. User's explicit instruction was "time out ... but if not all embeddings are complete we need to offer to continue," which this satisfies: `'timed_out'` status re-enables the form and shows a "Continue" button rather than just erroring out.
- **[2026-08-07] SUPERSEDES THE ABOVE:** user corrected this — "not time it, it should poll the tapis job" (see User Preferences). Real Tapis job-status polling is now the PRIMARY mechanism; the idle-activity timeout is demoted to a fallback only, used when (a) no job uuid is on record for a visit (legacy visits that predate this fix, or a submission whose uuid-persist step failed), or (b) the Tapis status poll itself raises (network/auth error — treated as transient, not proof of death). To make polling possible at all, `apply_embed_generate()` now captures `t.jobs.submitJob()`'s returned `job.uuid` and stores it via `GlobalDataStore('embeddings')` (`app/plugins/data_store.py`, existing infra — see next decision) rather than discarding it as before. Chose to still map even a `FINISHED` Tapis job to `'timed_out'` (not a new "complete" status) because the total expected tile count isn't tracked anywhere, so full completion can't be positively confirmed yet; re-POSTing `/embed` (Continue) stays safe/idempotent regardless (Decision 56 upsert).
- **[2026-08-07]** Chose `GlobalDataStore('embeddings')` (already-existing WebODM key-value store backed by the `PluginDatum` model, same one `coreplugins/ckan/publisher.py`'s `apply_ckan_publish()` uses to track its own async job state) to persist the Tapis job uuid per visit, over: (a) adding a column to `embeddingsdb`'s `visits` table — rejected, that DB is a separate externally-owned Postgres Pod with no extensible/JSONB column on `visits` (confirmed by re-reading `embeddings-tapis-actors/schema/embeddingsdb.sql` lines 109-147); (b) a new WebODM Django model/migration — rejected as unnecessary schema-change surface for a single string value. This keeps the change at Standard tier per repo CLAUDE.md (schema/API changes require the full Major-tier design-spec workflow) — no migration was needed anywhere.
